**Document status:** Single Source of Truth for Client App UX / functional design  
**Phase:** C2.2 — Product UX / Functional Specification ONLY  
**Date:** 2026-08-10  
**Depends on:** C2.1 Master Product Blueprint (repository audit)  
**Scope:** `mobile-app/client-app` only — Driver App out of scope  

**Classification legend (mandatory):**

| Label | Meaning |
|-------|---------|
| **REAL / EXISTING** | Implemented in Client App and backed by client-accessible backend |
| **PARTIAL** | Some real data/API; rest mock, stub, or incomplete |
| **MOCK** | UI exists; not production-backed for client role |
| **PLANNED** | Documented product intent / roadmap; not implemented |
| **MISSING** | Required for target product; not present |
| **REQUIRES DECISION** | Product/security choice needed before implementation |

**Hard rules:** Do not invent APIs. Do not treat mock UI as live ops. Messaging (M7–M9) is **PROTECTED**. Client must never consume admin/dispatcher-only endpoints as product features.

## 0. Product Statement

### What is FleetX Client App?

FleetX Client App is the **customer-facing mobile application** for company-linked client users. It lets a logistics customer:

1. Authenticate securely and see which company account they represent  
2. Communicate with FleetX dispatchers on authorized shipment-related conversations  
3. (When backend contracts exist) view and act on **their company’s shipments**, track status, and receive notifications  

Today the app is a **hybrid**: production messaging + auth, plus recovered premium product UI that is largely **MOCK** for shipments/tracking/notifications.

### CURRENT PRODUCT

Auth + identity + `dispatcher_customer` messaging (+ shipment communication handoff), wrapped in a premium shell with mock shipment/tracking/notification surfaces.

### TARGET PRODUCT

A calm, professional customer logistics app: identity-aware home, honest shipment/tracking experiences (client-scoped), protected messaging, notifications when contracted, clear profile/company, and never silent fake success.

### WHAT EXISTS (REAL)

JWT auth, SecureStore, `/auth/me`, `/auth/identity`, company link gate, conversation list/detail/send/read, Reverb + REST fallback, Message.id dedupe, shipment→conversation handoff (no auto-create).

### WHAT MUST BE BUILT (FRONTEND)

Honest navigation/shell, home without fake KPIs, unavailable states for unsupported domains, profile cleanup, deep-link integration points to messaging — then shipment/tracking/notification UIs **only after** client-safe APIs.

### WHAT REQUIRES BACKEND

Client-scoped shipment list/show/(optional create); client-safe tracking/status timeline; notifications API; register→company-link policy; optional password reset / SSO.

### WHAT MUST NEVER BE FAKED

Live GPS, ETA, driver PII, shipment lists “succeeding” without API, notification centers pretending unread counts, dashboard KPIs from ops endpoints, conversation auto-create, “Connected” realtime when transport is down.

## 2. Information Architecture

### 2.1 Evaluation of current 5-tab structure

Current tabs: **Home | Shipments | Tracking | Messages | Profile**

| Criterion | Assessment |
|-----------|------------|
| Frequency | Messages is highest real usage today; shipments/tracking are mock |
| Business importance | Shipments/tracking are target P1 ops; messaging is P0 ops today |
| Discoverability | Five tabs OK for mobile; Messages must stay a primary tab |
| Ergonomics | Bottom tabs match recovered design language |
| Scalability | Stack routes for details/handoff/notifications already fit |

**Decision: KEEP five tabs** as the primary IA.

**Rationale:** Matches recovered FleetX visual product, scales when shipment APIs arrive, and keeps Messages discoverable. Do **not** merge Tracking into Shipments until tracking has a client contract — until then Tracking tab shows honest **status/unavailable**, not fake maps.

### 2.2 Final IA tree

```
Client App
├── Splash / Session Gate          (/ )
├── Authentication
│   ├── Login                      (/login)
│   └── Register                   (/register)
├── Main Tabs
│   ├── Home                       (/(tabs)/ )
│   ├── Shipments                  (/(tabs)/shipments)
│   │   ├── [TARGET] List          (primary content when API exists)
│   │   ├── [TARGET] Create        (stack/modal — contract required)
│   │   └── [TARGET] Details       (stack — contract required)
│   ├── Tracking                   (/(tabs)/tracking)
│   ├── Messages                   (/(tabs)/messages)          ← PROTECTED
│   │   └── Conversation           (/conversation/[id])      ← PROTECTED
│   └── Profile                    (/(tabs)/profile)
│       ├── Company (section)
│       ├── Settings (supported only)
│       └── Support (→ Messages)
└── Contextual
    ├── Shipment communication handoff (/shipment/[id])       ← PROTECTED
    ├── Product shipment-details (/shipment-details)          ← MOCK until API
    └── Notifications (/notifications)                        ← MOCK until API
```

**Naming clarification (product):** Today’s Shipments tab is a **Create Shipment prototype**, not a list. Target: list-first; create secondary.

## 7. Messaging — Protected Foundation (M7–M9)

### 7.1 Do not redesign

Documented behavior (all **REAL / EXISTING**):

- Conversation list filtered `dispatcher_customer`  
- Isolation from driver threads  
- Detail: history, send, mark read  
- Dedupe by Message.id  
- Realtime: private channel + `.message.created`  
- REST fallback + Reconnect CTA + honest status labels  
- Handoff: find authorized conversation only — **no auto-create**  
- Client cannot create new threads (`conversation.manage` denied)  

**Out of scope / not supported:** typing, presence, receipts, attachments, new messaging APIs.

### 7.2 Product UX integration points only

| From | Action | To |

| Home | Open Messages | Messages tab |
| Shipment Details (future) | Contact dispatcher | `/shipment/{id}` handoff |
| Messages row | Open thread | `/conversation/{id}` |
| Notification (future) | Open conversation | `/conversation/{id}` |
| Issue / support | Contact FleetX | Messages |

## 18. Customer Journey Scenarios

1. **New → Login → Home:** Splash → Login → identity load → Home (real greeting; no fake shipments).  
2. **Messages:** Home → Messages → Conversation → send/receive (REAL).  
3. **Shipment → Details → Track:** Only after APIs; else Unavailable → Messages.  
4. **Issue → Dispatcher:** Details/Home → Contact → handoff or Messages → Conversation.  
5. **Notification:** Future API → deep link; today Unavailable → Messages.  
6. **Logout:** Profile → Logout → Login.  
7. **Session expires:** 401 → clear → Login.  
8. **No shipments:** Empty list (when API) or Unavailable (today).  
9. **No messages:** Existing empty state.  
10. **Unlinked company:** Banner; messaging disabled.  
11. **Feature unavailable:** Explicit unavailable, not mock success.  
12. **Network failure:** Error + Retry on fetch/send.
